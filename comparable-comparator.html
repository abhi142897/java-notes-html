Comparable vs Comparator

Sorting objects is one of the most common interview tasks, and it almost always comes down to this pair. The short version: Comparable defines an object's natural order — one, built into the class; Comparator defines external orders — as many as you like, outside the class.

Comparable — the natural order

  • Lives in java.lang; the class implements it and overrides compareTo().
  • Answers "how do objects of this type sort by default?"
  • compareTo returns a negative int (this < other), zero (equal), or positive (this > other).
Java
class Student implements Comparable<Student> {
    String name;
    int marks;

    @Override
    public int compareTo(Student other) {
        return this.marks - other.marks;   // natural order: by marks ascending
    }
}

List<Student> list = ...;
Collections.sort(list);          // uses compareTo, no extra argument
  • Because the order is built in, Collections.sort(list) and TreeSet/TreeMap "just work" with no extra argument.

⚠️ Avoid a - b for int fields in real code — it can overflow for large values. Prefer Integer.compare(this.marks, other.marks).

Comparator — external, swappable orders

  • Lives in java.util; you write a separate object and override compare(a, b).
  • Answers "sort these *this particular way*, right now" — by name, by marks descending, by multiple fields.
  • The class being sorted doesn't need to change (great when you can't edit it, e.g. a library class).
Java
// sort by name, without touching the Student class
Comparator<Student> byName = new Comparator<>() {
    public int compare(Student a, Student b) {
        return a.name.compareTo(b.name);
    }
};

Collections.sort(list, byName);   // pass the comparator in

The modern, readable form

Since Java 8 you rarely write the boilerplate above:

Java
list.sort(Comparator.comparing(s -> s.name));              // by name
list.sort(Comparator.comparingInt(s -> s.marks).reversed());// by marks, high to low

Comparator chaining (multi-field sort)

This is a favourite follow-up: "sort by marks descending, then by name."

Java
list.sort(
    Comparator.comparingInt((Student s) -> s.marks).reversed()
              .thenComparing(s -> s.name)      // tie-breaker
);
  • thenComparing only kicks in when the previous comparator reports a tie.

When to use which

  • Use Comparable when there's one obvious default order for the type (numbers by value, dates by time). One order, owned by the class.
  • Use Comparator when you need several orders, the order is context-specific, or you can't (or shouldn't) modify the class.
  • A clean design often does both: Comparable for the sensible default, plus Comparators for the alternate views.

Where you'll meet them

  • Collections.sort(), list.sort(), Arrays.sort().
  • TreeSet / TreeMap — order elements by Comparable, or by a Comparator passed to the constructor.
  • PriorityQueue — uses natural order, or a supplied Comparator.
  • Stream.sorted() — no-arg (natural) or sorted(comparator).

Common gotchas

  • If a class isn't Comparable and you call Collections.sort(list) with no comparator → ClassCastException at runtime.
  • Your ordering should be consistent with equals() for TreeSet/TreeMap; if compareTo returns 0 for two objects, the set treats them as duplicates even if equals says otherwise.
  • Keep compareTo/compare transitive and symmetric — an inconsistent comparator can throw IllegalArgumentException: Comparison method violates its general contract.
