Design Patterns

Design patterns are proven, reusable solutions to problems that show up again and again in software design. They are not code you copy — they are *templates for how to structure classes and objects*.

They fall into three families:

  • Creational — how objects are created (Singleton, Factory, Abstract Factory, Builder).
  • Structural — how objects are composed together (Adapter, Decorator, Proxy).
  • Behavioural — how objects talk to each other (Strategy, Observer).

The trick to remembering a pattern is to anchor it to a real-world picture. Each section below starts with one.

Singleton

Real-world picture: a country has exactly one sitting president at a time. No matter who asks, they all refer to the same person.

Problem: some things should exist only once in an app — a configuration manager, a logging service, a connection pool. Creating many copies wastes memory or causes conflicting state.

Solution: make the constructor private so nobody can new it, and hand out one shared instance.

Java
enum Config {                 // the simplest correct singleton
    INSTANCE;
    private int poolSize = 10;
    public int getPoolSize() { return poolSize; }
}

// usage
int size = Config.INSTANCE.getPoolSize();

Why the enum form? The JVM guarantees a single instance, and it is automatically thread-safe, serialization-safe, and reflection-safe (see the Reflection page for how a normal singleton can be broken). If you must use a class, the double-checked-locking form with a volatile field is the classic alternative.

In the wild: Spring beans are singletons by default; Runtime.getRuntime().

Factory Method

Real-world picture: you walk into a restaurant and order "a pizza". You don't build it — the kitchen decides *which* class of chef and steps produce it. You just get a pizza.

Problem: you want to create objects without hard-coding their exact class everywhere, so that adding a new type doesn't force you to edit every caller.

Solution: a factory method takes some input and returns the right object behind a common interface.

Java
interface Notification { void send(String msg); }
class EmailNotification implements Notification { public void send(String m){} }
class SmsNotification   implements Notification { public void send(String m){} }

class NotificationFactory {
    static Notification create(String channel) {
        return switch (channel) {
            case "email" -> new EmailNotification();
            case "sms"   -> new SmsNotification();
            default -> throw new IllegalArgumentException(channel);
        };
    }
}
// caller never says `new EmailNotification()`
Notification n = NotificationFactory.create("email");

Why it helps: the caller depends on the Notification interface, not concrete classes — that's the Dependency Inversion principle in action. Adding a PushNotification means adding one class and one case, nothing else changes.

In the wild: Calendar.getInstance(), NumberFormat.getInstance(), JDBC DriverManager.getConnection().

Abstract Factory

Real-world picture: a furniture showroom offers a *Victorian* set and a *Modern* set. If you pick Victorian, you want a Victorian chair *and* Victorian table *and* Victorian sofa — a matching family, never mixed.

Problem: you need to create *families* of related objects that must be used together, and you want to guarantee they match.

Solution: a factory that returns other factories — each concrete factory produces one whole family.

Java
interface Button { void paint(); }
interface Checkbox { void paint(); }

interface GUIFactory {                 // the abstract factory
    Button createButton();
    Checkbox createCheckbox();
}

class MacFactory implements GUIFactory {
    public Button createButton()   { return new MacButton(); }
    public Checkbox createCheckbox(){ return new MacCheckbox(); }
}
class WinFactory implements GUIFactory {
    public Button createButton()   { return new WinButton(); }
    public Checkbox createCheckbox(){ return new WinCheckbox(); }
}
// pick the family once; everything after matches
GUIFactory factory = new MacFactory();
Button b = factory.createButton();     // guaranteed a Mac-style button

In the wild: DocumentBuilderFactory, look-and-feel toolkits in UI frameworks.

Builder

Real-world picture: ordering a custom burger — bun, then patty, then cheese, then sauces — one choice at a time, and only at the end do you get the finished burger.

Problem: an object has many fields, several of them optional. A constructor with 8 arguments (a "telescoping constructor") is unreadable and error-prone (new Person("A", 25, null, true, null, ...)).

Solution: build the object step-by-step with readable, chainable calls, then build().

Java
class Person {
    private final String name;
    private final int age;
    private final String city;   // optional

    private Person(Builder b) { this.name=b.name; this.age=b.age; this.city=b.city; }

    static class Builder {
        private String name; private int age; private String city;
        Builder name(String n){ this.name=n; return this; }   // return this → chaining
        Builder age(int a){ this.age=a; return this; }
        Builder city(String c){ this.city=c; return this; }
        Person build(){ return new Person(this); }
    }
}
// readable, order-independent, optional fields skipped
Person p = new Person.Builder().name("Abhishek").age(25).build();

Why it helps: each call names what it sets, optional fields can be skipped, and the final object can be made immutable.

In the wild: StringBuilder, Stream.Builder, HttpRequest.newBuilder(), Lombok's @Builder.

Adapter

Real-world picture: a travel power plug adapter — your laptop's two-pin plug can't fit a UK socket, so the adapter sits in between and translates one shape into the other.

Problem: you have a class with a useful ability, but its interface doesn't match what your code expects (often a third-party or legacy class you can't change).

Solution: a wrapper that implements the interface your code wants, and internally delegates to the incompatible class.

Java
// what our app expects
interface PaymentGateway { void pay(int amountInPaise); }

// a third-party SDK we can't modify (works in rupees, different method name)
class LegacyRupeePay { void makePayment(double rupees) { /* ... */ } }

// adapter bridges the two
class RupeePayAdapter implements PaymentGateway {
    private final LegacyRupeePay legacy = new LegacyRupeePay();
    public void pay(int paise) { legacy.makePayment(paise / 100.0); }  // translate
}

In the wild: Arrays.asList() (array → List), InputStreamReader (byte stream → char stream).

Decorator

Real-world picture: a coffee. Start with plain coffee, wrap it with milk, wrap that with sugar. Each wrapper adds a bit of cost and behaviour, but it's still "a coffee" you can keep wrapping.

Problem: you want to add responsibilities to an object *at runtime* without creating a subclass for every combination (MilkCoffee, MilkSugarCoffee, MilkSugarCreamCoffee… explodes fast).

Solution: wrap the object in another object that implements the same interface and adds behaviour before/after delegating.

Java
interface Coffee { double cost(); }

class SimpleCoffee implements Coffee { public double cost(){ return 2.0; } }

abstract class CoffeeDecorator implements Coffee {   // wraps a Coffee
    protected final Coffee inner;
    CoffeeDecorator(Coffee c){ this.inner = c; }
}
class Milk extends CoffeeDecorator {
    Milk(Coffee c){ super(c); }
    public double cost(){ return inner.cost() + 0.5; }   // add, then delegate
}
class Sugar extends CoffeeDecorator {
    Sugar(Coffee c){ super(c); }
    public double cost(){ return inner.cost() + 0.2; }
}
// stack behaviours at runtime
Coffee order = new Sugar(new Milk(new SimpleCoffee()));  // 2.0 + 0.5 + 0.2 = 2.7

Decorator vs inheritance: inheritance fixes behaviour at compile time; decorators let you compose behaviour at runtime, in any order.

In the wild: the entire java.io library — new BufferedReader(new InputStreamReader(System.in)) is decorators stacked.

Proxy

Real-world picture: a company receptionist (or a bodyguard) stands in front of the boss. You talk to the receptionist; they check whether you're allowed in, maybe log your visit, and only then pass you through.

Problem: you want to control access to an object — add security, lazy-loading, caching, or logging — without changing the real object or the caller.

Solution: a proxy implements the same interface as the real object, does its extra work, then forwards the call.

Java
interface Image { void display(); }

class RealImage implements Image {          // expensive to create
    RealImage(String file){ /* loads from disk NOW */ }
    public void display(){ /* draw */ }
}

class ImageProxy implements Image {          // stands in for RealImage
    private final String file;
    private RealImage real;                  // not loaded yet
    ImageProxy(String file){ this.file = file; }
    public void display(){
        if (real == null) real = new RealImage(file);  // lazy-load on first use
        real.display();
    }
}
// the heavy object is only built when actually needed
Image img = new ImageProxy("photo.png");     // cheap
img.display();                               // now it loads

Proxy vs Decorator: they look similar (both wrap and implement the same interface). The intent differs — a decorator adds behaviour, a proxy controls access (security, laziness, remoting, caching).

In the wild: Spring AOP (transactions, @Transactional), Hibernate lazy-loaded entities, RMI remote stubs.

Strategy

Real-world picture: Google Maps asks how you want to travel — drive, walk, or cycle. The goal ("get me a route") is the same; the *algorithm* used differs, and you can switch it any time.

Problem: you have several interchangeable ways to do one thing and don't want a giant if/else that you must edit every time a new way appears.

Solution: put each algorithm behind a common interface and let the caller plug in whichever one they want at runtime.

Java
interface PaymentStrategy { void pay(int amount); }
class UpiPayment  implements PaymentStrategy { public void pay(int a){ /* UPI */ } }
class CardPayment implements PaymentStrategy { public void pay(int a){ /* card */ } }

class Checkout {
    private PaymentStrategy strategy;                 // the current algorithm
    void setStrategy(PaymentStrategy s){ this.strategy = s; }
    void checkout(int amount){ strategy.pay(amount); }// delegates to whichever is set
}
// swap freely at runtime
Checkout c = new Checkout();
c.setStrategy(new UpiPayment());   c.checkout(500);
c.setStrategy(new CardPayment());  c.checkout(900);

Why it helps: adding a new payment method is a new class, not an edit to Checkout. That's the Open/Closed principle.

In the wild: Comparator passed to Collections.sort() is a strategy; ThreadPoolExecutor's rejection policies.

Observer

Real-world picture: a YouTube channel. When it uploads a video, every subscriber is notified automatically. The channel doesn't know or care who the subscribers are — it just broadcasts.

Problem: when one object changes, several others need to react — and you don't want the changing object tightly coupled to all of them.

Solution: the subject keeps a list of observers and notifies them all on change. Observers can subscribe/unsubscribe freely.

Java
interface Observer { void update(String news); }

class Channel {                              // the subject
    private final List<Observer> subs = new ArrayList<>();
    void subscribe(Observer o){ subs.add(o); }
    void unsubscribe(Observer o){ subs.remove(o); }
    void upload(String video){
        for (Observer o : subs) o.update(video);   // notify everyone
    }
}
class User implements Observer {
    private final String name;
    User(String n){ this.name = n; }
    public void update(String video){ /* name gets notified of video */ }
}
// wiring
Channel ch = new Channel();
ch.subscribe(new User("Abhishek"));
ch.subscribe(new User("Riya"));
ch.upload("Design Patterns in 20 min");     // both users notified

Why it helps: the subject and observers are loosely coupled — either side can change independently. This is the backbone of event systems.

In the wild: Java's EventListener (button clicks), reactive streams (Flow.Publisher/Subscriber), messaging pub/sub.
