Serialization

What it is

  • Serialization = turning an object (its state) into a byte stream so it can be saved to a file, stored in a cache, or sent across a network.
  • Deserialization = rebuilding the object from those bytes.
  • Think of it as *freezing* an object now and *thawing* it later, possibly on another machine or after a restart.

Making a class serializable

  • Implement the marker interface Serializable (it has no methods — it just flags the class as "OK to serialize").
Java
import java.io.Serializable;

class Employee implements Serializable {
    int id;
    String name;
}
  • Writing and reading:
Java
// serialize -> bytes -> file
try (ObjectOutputStream out =
         new ObjectOutputStream(new FileOutputStream("emp.ser"))) {
    out.writeObject(employee);
}

// deserialize <- bytes <- file
try (ObjectInputStream in =
         new ObjectInputStream(new FileInputStream("emp.ser"))) {
    Employee e = (Employee) in.readObject();
}

serialVersionUID — the version stamp

  • A long that identifies the "version" of a serializable class.
Java
private static final long serialVersionUID = 1L;
  • On deserialization, the JVM compares the UID in the bytes with the UID of the current class.
  • Match → proceed.
  • Mismatch → InvalidClassException.
  • If you don't declare one, the compiler generates it from the class structure — so *any* change (a new field, a changed method signature) silently changes the UID and breaks old serialized data.
  • 👉 Always declare serialVersionUID explicitly for classes you serialize, so you stay in control of compatibility.

transient — skip a field

  • Mark a field transient to exclude it from serialization.
Java
class User implements Serializable {
    String name;
    transient String password;   // never written to the byte stream
    transient Connection dbConn;  // makes no sense to serialize
}
  • On deserialization, transient fields come back as defaults (null for objects, 0 for numbers, false for boolean).
  • Use it for: secrets (passwords, tokens), and things that can't/shouldn't be frozen (DB connections, threads, sockets, caches you can rebuild).

Key rules and behaviours

  • static fields are not serialized — they belong to the class, not the instance.
  • The whole object graph is serialized: if Employee references an Address, then Address must also be Serializable, or you get NotSerializableException.
  • The constructor is not called during deserialization — the object is rebuilt directly from bytes.
  • A superclass that isn't Serializable must have a no-arg constructor; its fields are re-initialised via that constructor, not restored from bytes.

Customising: writeObject / readObject

  • For special handling (e.g. encrypt a field, or restore a transient field), a class can define these private methods and the JVM will call them:
Java
private void writeObject(ObjectOutputStream out) throws IOException {
    out.defaultWriteObject();        // write the normal fields
    // ...custom logic (e.g. write an encrypted value)
}
private void readObject(ObjectInputStream in)
        throws IOException, ClassNotFoundException {
    in.defaultReadObject();          // read the normal fields
    // ...custom logic (e.g. rebuild a transient field)
}

Security note (why interviewers ask)

  • Deserializing untrusted bytes is dangerous — crafted input can trigger "deserialization attacks" (arbitrary code execution via gadget chains).
  • Guidance: never deserialize data you don't trust; prefer safer formats (JSON via Jackson/Gson, or Protobuf) for external data; validate aggressively.

Quick recall

  • Serializable → marker interface, opt-in.
  • serialVersionUID → version guard; declare it yourself.
  • transient → skip this field (secrets, unfreezable resources).
  • static → never serialized.
  • Referenced objects must be serializable too (whole graph).
