SOLID Principles

SOLID is five design principles that keep object-oriented code easy to change, test, and extend. They're less about clever code and more about *where responsibilities live*. Interviewers love asking for a one-line definition plus an example — so each principle below has both.

S — Single Responsibility Principle (SRP)

A class should have only one reason to change — it should do one job.

Picture: a Swiss-army knife is handy, but a kitchen uses separate knives because each does its job better and can be replaced independently.

Smell: an Invoice class that calculates totals, saves to the database, *and* emails the customer. Three unrelated reasons to change tangled in one place.

Fix: split into InvoiceCalculator, InvoiceRepository, and InvoiceMailer. Each changes for exactly one reason.

O — Open/Closed Principle (OCP)

Software should be open for extension but closed for modification — add new behaviour without editing tested code.

Picture: a phone with app support. You add features by installing apps, not by cracking open the phone and re-soldering it.

Smell: a discount() method with a growing if (type == GOLD) … else if (type == SILVER) … that you edit for every new tier.

Fix: define a DiscountPolicy interface and add a new class per tier. Existing code isn't touched — this is exactly what the Strategy pattern enables.

L — Liskov Substitution Principle (LSP)

A subclass must be usable anywhere its parent is, without surprising the caller.

Picture: if a recipe calls for "milk", almond milk should work. But if a "milk" that secretly curdles when heated is passed in, it breaks the recipe — that subtype violates the contract.

Smell: the classic Square extends Rectangle. Setting width and height independently is valid for a rectangle but breaks for a square, so a Square can't safely stand in for a Rectangle.

Fix: don't force an "is-a" that breaks behaviour. Model them separately, or use a common abstraction that both honour.

I — Interface Segregation Principle (ISP)

Don't force a class to implement methods it doesn't use — prefer several small interfaces over one fat one.

Picture: a printer-scanner-fax combo forces a plain printer to "implement" scan and fax with dummy code. Split the buttons so each device only exposes what it can do.

Smell: a Worker interface with work() *and* eat(). A RobotWorker is forced to implement eat() with an empty or throwing method.

Fix: split into Workable and Eatable; classes implement only what applies.

D — Dependency Inversion Principle (DIP)

Depend on abstractions, not concrete classes — high-level code shouldn't be nailed to low-level details.

Picture: a wall socket. Your laptop depends on the *socket shape* (an abstraction), not on the specific power plant. Swap the source behind the socket and the laptop neither knows nor cares.

Smell: OrderService that does new MySQLDatabase() inside itself — now it's welded to MySQL and can't be tested with a fake.

Fix: depend on a Database interface and have the concrete DB *injected* in (constructor injection). This is the idea behind Spring's dependency injection.

Why they work together

SRP keeps classes focused, ISP keeps interfaces focused, OCP lets you add without breaking, LSP keeps inheritance honest, and DIP keeps the wiring flexible. Follow them and features tend to become "add a new class", not "edit ten existing ones".
