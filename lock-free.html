Multithreading — Lock-Free

Lock-free concurrency is a technique in multithreading where threads operate on shared data without using locks (like synchronized or ReentrantLock), while still ensuring correctness.

CAS

Lock-free concurrency uses CAS (compare and Swap) technique:

  • It’s a low level operation.
  • It’s Atomic.
  • And all modern Processor supports it.

It involves 3 main parameters:

  • Memory location: location where variable is stored.
  • Expected Value: value which should be present at the memory.
  • ABA problem is solved using version or timestamp.
  • New Value: value to be written to memory, if the current value matches the expected value.
  • Execution flow:
  1. Thread reads value
  2. Prepares updated value
  3. Uses CAS to update
  4. If another thread changed it → retry
  • No waiting, no blocking

ABA problem

  • ABA problem happens when a value changes from A → B → A, and a thread falsely assumes nothing has changed.
  • CAS checks "If current value == expected value → update". It does NOT check history, only current value.

⚙️ Step-by-Step Example

Initial value:
X = A
Thread T1:

  1. Reads X = A
  2. Plans to update A → C (but gets paused)

Thread T2:

  1. Changes A → B
  2. Then changes B → A (back to original)

Thread T1 resumes:

  1. Sees X = A (same as before)
  2. CAS succeeds ✅
  • BUT ❌ Data was modified in between!

Solution to ABA Problem (Use Versioning (Stamp))

Java
AtomicStampedReference<Integer> ref =
    new AtomicStampedReference<>(100, 1);

How it works:

(A, version 1)

After changes:
(A, version 3)

Atomic variables

Atomic => single or "all or nothing"

Example usage:
Basic single thread code -

Java
public class Practice {
    public static void main(String[] args) {
        Buffer buffer = new Buffer();
        for (int i = 0; i < 400000; i++) {
            buffer.increment();
        }
        System.out.println(buffer.get());
    }
}


class Buffer {
    int counter;

    public void increment() {
        counter++;
    }

    public int get() {
        return counter;
    }
}

Using Multiple threads -

Java
public class Practice {
    public static void main(String[] args) {
        Buffer buffer = new Buffer();
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 100000; i++) {
                buffer.increment();
            }
        });

        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 100000; i++) {
                buffer.increment();
            }
        });

        Thread t3 = new Thread(() -> {
            for (int i = 0; i < 100000; i++) {
                buffer.increment();
            }
        });

        Thread t4 = new Thread(() -> {
            for (int i = 0; i < 100000; i++) {
                buffer.increment();
            }
        });

        t1.start();
        t2.start();
        t3.start();
        t4.start();

        try{
            t1.join();
            t2.join();
            t3.join();
            t4.join();
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }

        System.out.println(buffer.get());
    }
}

Output:

diagram
350452

We will get different output every time (inconsistent behavior).

We can fix this using:

  1. Using lock (synchronized):
Java
public synchronized void increment() {
    counter++;
}
  1. Using lock free operation (AtomicInteger)
Java
class Buffer {
    AtomicInteger counter =  new AtomicInteger(0);

    public void increment() {
        counter.getAndIncrement();
    }

    public int get() {
        return counter.get();
    }
}

Atomic vs Volatile

When you launch an application, the operating system creates a process. That process spawns threads to execute specific pieces of code. The OS scheduler then assigns these threads to available CPU cores (or logical threads) to be processed. This allows for parallelism, where different parts of a program run at the exact same time on different cores.

🔁 CPU and Memory Hierarchy Recap

When a Java variable is accessed or modified, it doesn't always go directly to RAM. Instead:

  1. Each CPU core has its own L1 and L2 cache (super-fast small memory).
  2. There’s a shared RAM (main memory) that all cores can access.
  3. To improve performance, CPU caches hold copies of variables from RAM.
  4. Problem: Caches can go stale. One thread running on Core-1 may not see the latest value modified by another thread on Core-2 unless there's synchronization.

volatile

  • Guarantees
  • Visibility only.
  • Ensures updates to a variable are always visible to all threads.
  • Does NOT guarantee atomicity (i.e., read-modify-write is not atomic).

⚙ How it works w.r.t CPU

  • When a thread writes to a volatile variable:
  • The new value is written directly to RAM (main memory).
  • Other threads reading it will bypass their CPU cache and read from RAM or updated cache via cache coherency protocol.
  • CPU’s cache coherence protocols (like MESI) ensure the changes are propagated to other CPU cores.
  • ❌ Does not prevent race conditions
Java
volatile int counter = 0;
public void increment() {
    counter
}

Even with volatile, two threads can read the same value, increment, and write the same result, losing one increment.

AtomicInteger and other atomic classes

  • Guarantees
  • Both atomicity and visibility.
  • Uses low-level CPU instructions (like compare-and-swap - CAS) to ensure atomic updates.

⚙ How it works w.r.t CPU

  • Performs atomic operations at hardware level, which:
  • Locks the memory bus or uses CPU-level atomic instructions.
  • These bypass issues with L1/L2 caches because they use CPU cache coherency and atomic primitives.

🧠 In simpler words

The atomic operation is like asking the CPU: "If the value is still X, update it to Y" in a single, uninterruptible step.

Java
AtomicInteger counter = new AtomicInteger(0);
public void increment() {
    counter.incrementAndGet(); // Atomic and thread-safe
}
