Sealed Interface (java 17)

  • A sealed interface restricts which classes can implement it.

Problem (before Java 17)

Java
interface Shape {}
  • Anyone can implement it:
Java
class RandomClass implements Shape {} // ❌ uncontrolled
  • Solution: Sealed Interface
Java
sealed interface Shape permits Circle, Rectangle {}
  • Only these classes allowed:
diagram
Circle
Rectangle
  • Example
Java
sealed interface Shape permits Circle, Rectangle {}

final class Circle implements Shape {
    double radius;
}

final class Rectangle implements Shape {
    double length, width;
}

Important Rules

  1. Use permits
Java
sealed interface Shape permits A, B {}
  1. Subclasses must declare one of:
  • final
Java
final class Circle implements Shape {}
  • Cannot be extended further
  • sealed
Java
sealed class Rectangle implements Shape permits Square {}
  • Further restricts hierarchy
  • non-sealed
Java
non-sealed class Triangle implements Shape {}
  • Opens hierarchy again
  1. All permitted classes must be:
  • In same package (or module)
  • Must explicitly declare: final, sealed, or non-sealed

New Switch in Java 14+

  • Switch can now be used as an expression (returns a value) and supports a cleaner syntax using ->.

Problems with Old Switch

Java
int day = 2;
String result;

switch (day) {
    case 1:
        result = "Monday";
        break;
    case 2:
        result = "Tuesday";
        break;
    default:
        result = "Invalid";
}
  • New Switch (Java 14+)
Java
int day = 2;

String result = switch (day) {
    case 1 -> "Monday";
    case 2 -> "Tuesday";
    default -> "Invalid";
};
  • Too much boilerplate
  • Forget break → bugs
  • Not concise

Key Features

  1. Switch as Expression
  • Returns value directly
Java
String result = switch (day) {
    case 1 -> "Mon";
    case 2 -> "Tue";
    default -> "NA";
};
  1. Arrow Syntax (->)
Java
case 1 -> "Monday";   // No break needed ❌
  1. Multiple Labels
Java
case 1, 2, 3 -> "Weekday";
  1. Block with yield
Java
String result = switch (day) {
    case 1 -> {
        System.out.println("Monday logic");
        yield "Monday";    // yield returns value from block
    }
    default -> "Other";
};
  1. Switch expression must be exhaustive
Java
default -> "Invalid";

OR cover all cases

Example

Java
public class SwitchExample {
    public static void main(String[] args) {

        int day = 3;

        String type = switch (day) {
            case 1, 2, 3, 4, 5 -> "Weekday";
            case 6, 7 -> "Weekend";
            default -> "Invalid";
        };

        System.out.println(type);
    }
}

Pattern Matching (java 16+)

  • Pattern matching allows you to test a type and extract data in a single step.

Pattern Matching with instanceof

Problem Before Pattern Matching

Java
if (obj instanceof String) {
    String str = (String) obj; // explicit cast ❌
    System.out.println(str.length());
}
  • With Pattern Matching
Java
Object obj = "Hello";
if (obj instanceof String str) {
    // str is accessible here
    System.out.println(str.length());
}

Variable is only available inside the true block

Pattern Matching with Switch

Java
static String check(Object obj) {
    return switch (obj) {
        case String s -> "String: " + s;
        case Integer i -> "Integer: " + i;
        default -> "Unknown";
    };
}

No casting needed

Pattern Matching with Sealed Classes

Java
sealed interface Shape permits Circle, Rectangle {}

record Circle(double radius) implements Shape {}
record Rectangle(double length, double width) implements Shape {}

static double area(Shape shape) {
    return switch (shape) {
        case Circle c -> Math.PI * c.radius() * c.radius();
        case Rectangle r -> r.length() * r.width();
    };
}

All cases handled ✅ (no default needed)

Record (java 16+)

  • A record is a special class used to model immutable data with minimal boilerplate.

❓ Problem Before Records

Java
class Person {
    private final String name;
    private final int age;

    public Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    public String getName() { return name; }
    public int getAge() { return age; }

    public boolean equals(Object o) { ... }
    public int hashCode() { ... }
    public String toString() { ... }
}
  • Too much boilerplate
  • Solution: Record
Java
record Person(String name, int age) {}
  • That’s it! 🚀

What Java Generates Automatically
For:

Java

  • Private final fields
  • Constructor

  • hashCode()
  • toString()

Text Blocks (Java 15)

  • Multi-line string literals without messy escaping or concatenation.

Problem before Text Blocks:

Java
String json = "{\n" +
              "  \"name\": \"Abhishek\",\n" +
              "  \"role\": \"SDE\"\n" +
              "}";

With Text Blocks:

Java
String json = """
    {
      "name": "Abhishek",
      "role": "SDE"
    }
    """;
  • Opens and closes with triple quotes """.
  • Newlines and quotes need no escaping.
  • Incidental leading whitespace is stripped based on the closing """ position.

var — Local Variable Type Inference (Java 10)

  • The compiler infers the type from the right-hand side. Java stays statically typed — var is not any.
Java
var list = new ArrayList<String>();  // inferred as ArrayList<String>
var count = 10;                      // inferred as int
var name = "Abhishek";               // inferred as String
  • Only for local variables (inside methods).
  • ❌ Not allowed for fields, method parameters, or return types.
  • ❌ Cannot be used without an initializer, and cannot be initialized to null.
  • Improves readability; no runtime cost.

Optional (Java 8)

  • A container that may or may not hold a non-null value — a cleaner alternative to returning null, and a defense against NullPointerException.

The problem it solves. Imagine looking up a user, then their address, then their city:

Java
// returns null when not found
String city = userRepo.findByName("Abhishek")   // User or null
                      .getAddress()              // 💥 NPE if user was null
                      .getCity();                // 💥 NPE if address was null

One missing value anywhere and you get a NullPointerException. The defensive fix is a pyramid of null checks:

Java
String city = "UNKNOWN";
User user = userRepo.findByName("Abhishek");
if (user != null) {
    Address addr = user.getAddress();
    if (addr != null && addr.getCity() != null) {
        city = addr.getCity();
    }
}

Ugly, easy to forget a check, and the "not found" case is invisible in the method signature.

With Optional the chain short-circuits safely, and the return type *tells the caller* a value might be missing:

Java
Optional<User> findByName(String name) { ... }   // signature is honest: may be empty

String city = userRepo.findByName("Abhishek")
        .map(User::getAddress)     // skipped if user is empty
        .map(Address::getCity)     // skipped if address is empty
        .orElse("UNKNOWN");        // one clear fallback

No manual null checks, no NPE, and anyone reading Optional<User> immediately knows the lookup can come back empty.

Creating and reading Optionals:

Java
Optional<String> name  = Optional.of("Abhishek");     // must be non-null
Optional<String> maybe = Optional.ofNullable(getName()); // may be null
Optional<String> empty = Optional.empty();

name.ifPresent(n -> System.out.println(n));  // runs only if present
  • Common methods:
MethodPurpose
of(x)Wrap a non-null value (throws if null)
ofNullable(x)Wrap a value that might be null
empty()An empty Optional
isPresent()Is a value present?
ifPresent(fn)Run code only if present
orElse(default)Value, or a default
orElseGet(sup)Value, or lazily computed default
orElseThrow()Value, or throw
map(fn)Transform the value if present
  • ✅ Best used as a return type so callers must consciously handle "empty". ❌ Avoid Optional fields and method parameters.
  • ⚠️ Don't just call .get() — it throws if empty, which defeats the purpose. Prefer orElse / orElseThrow / map.

Record Patterns (Java 21)

  • Deconstruct a record directly inside a pattern — pattern matching + records combined.
Java
record Point(int x, int y) {}

static String describe(Object o) {
    return switch (o) {
        case Point(int x, int y) -> "x=" + x + ", y=" + y; // components extracted
        default -> "not a point";
    };
}
  • Pulls the record's components out in a single step, no manual accessors.

Strings & Immutability

Why String gets its own topic

  • The most-used class in Java, and an interview favourite.
  • String is immutable — once created, its contents can never change. Any "modification" produces a new String.

String Constant Pool (SCP)

  • A special region inside the heap that stores string literals.
  • Two literals with the same text share one object, saving memory.
Java
String s1 = "hi";
String s2 = "hi";              // same pooled object as s1
String s3 = new String("hi");  // NEW object in heap (+ "hi" kept in pool)

System.out.println(s1 == s2);       // true  -> same pool reference
System.out.println(s1 == s3);       // false -> different objects
System.out.println(s1.equals(s3));  // true  -> same content
  • == compares references; .equals() compares content.

Why is String immutable?

  1. String pool works — many references can safely share one object only because it never changes.
  2. Security — Strings hold usernames, URLs, file paths, DB credentials. If mutable, a value could be changed *after* it was validated.
  3. Thread-safety — immutable objects are automatically safe to share across threads.
  4. Cached hashCode — String caches its hash code, which makes it a fast, reliable HashMap key (safe only because it never changes).
  5. Class loading — class names are Strings; immutability prevents tampering with what gets loaded.

intern()

  • Returns the pooled reference for a string's content.
Java
String s3 = new String("hi");
String s4 = s3.intern();       // pooled reference
System.out.println(s1 == s4);  // true

Common interview traps

  1. Compile-time constant folding — both sides are constants, folded to one literal:
Java
String a = "ab";
String b = "a" + "b";        // folded to "ab" at compile time
System.out.println(a == b);  // true
  1. Runtime concatenation — a variable is involved, so a new object is built at runtime:
Java
String p = "a";
String q = p + "b";          // built at runtime
System.out.println(a == q);  // false (use .equals for content)
  1. String is final → it cannot be subclassed.
  2. Every "change" (concat, replace, toUpperCase...) returns a new String; the original is untouched.

equals() and hashCode()

Default behaviour (from Object)

  • Object.equals() → reference equality (same as ==).
  • Object.hashCode() → an int based on the object's identity, not its data.
  • So two objects with identical fields are not equal by default.

Why override them?

  • To make objects equal by value (e.g. two Person objects with the same id).
  • Absolutely required when objects are used as keys in a HashMap or elements in a HashSet.

The contract (must-know)

  1. If a.equals(b) is true, then a.hashCode() == b.hashCode() must be true.
  2. If a.hashCode() != b.hashCode(), then a.equals(b) must be false.
  3. Equal hash codes do not guarantee equality — different objects may share a hash code (a collision), and that is allowed.
  4. equals must be reflexive, symmetric, transitive, and consistent; and a.equals(null) is always false.
  • Golden rule: if you override equals(), you must override hashCode() — otherwise hash-based collections break.

How HashMap uses both

  1. hashCode() decides which bucket a key belongs to.
  2. Inside that bucket, equals() finds the exact key.

So if two "equal" keys return different hash codes, the map looks in different buckets and fails to find the entry — you get duplicates or lost values.

Correct implementation

Java
import java.util.Objects;

class Person {
    String name;
    int id;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                       // same reference
        if (o == null || getClass() != o.getClass()) return false;
        Person p = (Person) o;
        return id == p.id && Objects.equals(name, p.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);                    // consistent with equals
    }
}

Common mistakes

  • Overriding equals but not hashCode → a HashSet will happily store "duplicate" objects.
  • Using mutable fields inside hashCode() → if the field changes, the object is "lost" in the map (wrong bucket).
  • Comparing object fields with == inside equals() → use .equals() / Objects.equals() instead.
  • Forgetting the null and different-class checks → NullPointerException or wrong results.
